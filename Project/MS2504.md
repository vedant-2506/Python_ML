# RankResume --- Project Work Log

## **Date:** 20 Sep 2026

**Subject:** **ATS Calculations (Rule-based Score)**

-   **Code Pipeline (already done):**

    -   PDF/Doc/Docx -> read text -> store raw text in DB -> extract
        name, email, phone.

    -   Apply NLP preprocessing -> store in DB -> create JSON from NLP
        data and technology DB -> store in DB.

    -   Files: `/project/DB_Store/rankresume_pipeline.ipynb` and
        `/project/DB_Store/rankresume_pipeline.py`.

    -   After the resume and JD JSON (`structured_data`) was final, I
        built the code to calculate the ATS score and rank candidates.

-   **Folder structure:**

    -   All ATS work is in `/Python-ML/Project/ATS_calculation`.

    -   `LLM_based` has `llm_scorer.py`. `rule_based` has
        `rule_based_calculator.py` and `text_utils.py`.

    -   `ats_calculator.py` and `ranking.py` are in the main folder.

-   **Database:**

    -   Added a new table `ats_score` (the `candidate` and
        `job_description` tables already existed).

    -   Columns: `candidate_id`, `jd_id`, `keyword_score`,
        `similarity_score`, `title_score`, `experience_score`,
        `education_score`, `achievement_score`, `rule_based_score`,
        `llm_based_score`, `final_ats_score`.

    -   The final ATS score is also saved in the `ats_score` column of
        the `candidate` table.

-   **Files created:**

    -   `ats_calculator.py` -> final score (rule-based + LLM).

    -   `rule_based_calculator.py` -> 6 factors, each with an evidence
        line.

    -   `text_utils.py` -> text cleaning, skill aliases, stemming,
        experience text to years.

    -   `llm_scorer.py` -> sends resume and JD JSON to Ollama and reads
        the score.

    -   `ranking.py` -> ranks candidates by `ats_score`.

-   **Rule-based score (6 factors with weights):**

    -   Keyword 35% -> JD required skills found in the resume.

    -   Similarity 20% -> how relevant the projects are to the JD
        skills.

    -   Title 10% -> JD job title vs candidate's past roles.

    -   Experience 15% -> candidate years vs required years. Full marks
        if equal or more, partial if less.

    -   Education 15% -> degree level (PhD > Master > Bachelor > Diploma
        > 12th) plus marks. GPA, CGPA, and percentage are all converted
        to 0-100.

    -   Achievement 5% -> required certificates vs candidate's
        certificates.

-   **Keyword matching is not only exact match:**

    -   Exact skill = 1.0, skill inside a longer skill (`python` in
        `python programming`) = 0.95, found in project/experience text =
        0.9, spelling variant = 0.9, implied skill (`version control`
        from `git`) = 0.7.

    -   Partial match on multi-word keywords gets up to 0.75.

    -   Aliases work: `js` -> `javascript`, `k8s` -> `kubernetes`,
        `postgres` -> `postgresql`.

    -   C++, C#, .NET, and Node.js are kept correctly.

-   **Similarity and title:**

    -   Uses `sentence-transformers` (MiniLM) if installed. Otherwise
        falls back to word overlap, so the code never breaks.

-   **Fresher handling:**

    -   If the JD does not ask for a factor, or the candidate has no
        data for it, that factor is dropped and the remaining weights
        are scaled back to 100%.

    -   So freshers are not punished for having no job title or
        experience.

    -   If the score is below 50 but keyword and similarity both have
        some match, it is lifted slightly towards 50.

-   **Output:** each factor gives a score and an evidence line (example:
    "Matched 6 of 8 required keywords. Missing: ..."), so results are
    easy to explain.

## **Date:** 26 Sep 2026

**Subject:** **LLM Score, Final ATS Score and Ranking**

-   **LLM score:**

    -   The Ollama model (`llama3.2` by default) gets the resume and JD
        JSON and returns `{"score": ..., "reason": ...}`.

    -   The prompt says to use only the given JSON and not invent
        anything.

    -   It uses the same factor weights and does not punish freshers.

    -   Temperature is 0 and JSON output is requested for consistent
        results.

    -   Score reading handles JSON, code fences, `78/100`, and
        `score: 78`. Values outside 0-100 are rejected.

    -   Model name, URL, and timeout are set through environment
        variables.

-   **Final score:** `60% rule-based + 40% LLM`. If the LLM fails, the
    rule-based score is used, so the pipeline never breaks.

    -   `compute_final_ats(jd, resume)` returns the rule-based score,
        LLM score, LLM reason, final score, and factor details. Use
        `use_llm=False` for rule-based only.

-   **Ranking:**

    -   Candidates with an `ats_score` are sorted high to low.

    -   Equal scores get the same rank (example: 1, 2, 2, 4).

## **Date:** 1 Oct 2026

**Subject:** **Migration from Ollama to Gemini API**

-   Moved the LLM scorer from local Ollama to the Gemini API.

-   `llm_scorer.py` now uses the Gemini Python SDK. The API key comes
    from `GEMINI_API_KEY` (stored in `.env`, not in the code).

-   Model and timeout are set with `GEMINI_MODEL` and `GEMINI_TIMEOUT`.

-   Function names and signatures are unchanged, so the rest of the
    pipeline needs no changes. `get_ollama_evaluation()` and
    `get_ollama_score()` keep their old names but now call Gemini.

-   Same purpose as before: send resume and JD JSON, get a valid 0-100
    score and reason.

-   The Gemini client is cached and reused for all candidates.

-   Handles invalid API key, unavailable model, rate limit, quota
    exhaustion, and server errors.

-   Temporary errors are retried with backoff. Permanent errors or quota
    problems stop further Gemini requests for that run.

-   If Gemini fails or gives an empty, malformed, or invalid response,
    the LLM score is `None` and the rule-based score is used.

## **Date:** 02 Oct 2026

**Subject:** **Gemini API Testing and Error Handling**

-   `test_gemini.py` (smoke test) confirmed the API key and model work.

-   `test_llm_scorer.py` tested valid responses and failure cases. All
    tests passed.

-   Score extraction is flexible: it reads JSON score fields, plain
    numbers, `score: 85`, and `85/100`, and rejects values outside
    0-100.

-   A real score of `0` is different from a failed response (`None`), so
    an API failure is never counted as a zero score.


**Subject:** **Gemini Free-Tier Quota and Pipeline Protection**

-   The Gemini free-tier limit was reached while testing many resumes
    against one JD.

-   Each `generate_content` call uses one request, even if the JD is the
    same.

-   A quota error (HTTP `429 RESOURCE_EXHAUSTED`) is handled
    differently from a temporary failure.

-   When the daily quota is used up, the scorer stops sending more
    requests.

-   The rule-based score keeps working without Gemini.

-   With a limited quota, run a one-pair smoke test before the full
    pipeline.
