**Subject:** **ATS Calculations (Rule-based Score)**

* **Code Pipeline (already done):**

* After the JSON structure was finalized (resume and JD `structured_data`), I worked on the code that calculates the ATS score of a candidate against a JD and ranks the candidates.


* **Folder structure:**

* All ATS work is in `/Python-ML/Project/ATS_calculation`.


* It has 2 folders: `LLM_based` (has `llm_scorer.py`) and `rule_based` (has `rule_based_calculator.py` and `text_utils.py`).


* `ats_calculator.py` and `ranking.py` are in the `ATS_calculation` folder.


* **Database:**

* `rankresume` DB already has `candidate` and `job_description` tables. One more table created: `ats_score`.


* `ats_score` table columns: `candidate_id`, `jd_id`, `keyword_score`, `similarity_score`, `title_score`, `experience_score`, `education_score`, `achievement_score`, `rule_based_score`, `llm_based_score`, `final_ats_score`.


* From the `candidate` table, the `ats_score` column is used to store the final ATS score.


* **Files created:**

* `ats_calculator.py` -> final score, combines the rule-based score and the LLM score.


* `rule_based_calculator.py` -> deterministic scoring, has 6 factors and gives evidence for each factor.


* `text_utils.py` -> helper functions: text normalization, skill aliases, stemming, and converting experience text into years.


* `llm_scorer.py` -> sends resume JSON and JD JSON to the local Ollama model and reads the score.


* `ranking.py` -> reads `ats_score` from the `candidate` table and gives rank.


* **Rule-based score (6 factors with weights):**

* Keyword 35% -> required skills of the JD matched with resume skills.


* Similarity 20% -> project relevance with the JD skills.


* Title 10% -> JD job title compared with candidate's previous roles.


* Experience 15% -> candidate years vs required years. Full marks if equal or more, partial marks if less.


* Education 15% -> degree level (PhD > Master > Bachelor > Diploma > 12th) plus marks. Marks in 4-point GPA, 10-point CGPA, and percentage are all converted to 0-100.


* Achievement 5% -> required certificate/achievement matched with the candidate's certificates.


* **Keyword matching is not only exact match:**

* Exact skill = 1.0, skill inside a longer skill (`python` in `python programming`) = 0.95, found in project/experience text = 0.9, spelling variant = 0.9, implied skill (`version control` from `git`/`github`) = 0.7.


* Partial words match on multi-word keywords also gets some marks (up to 0.75).


* Aliases are handled, like `js` -> `javascript`, `k8s` -> `kubernetes`, `postgres` -> `postgresql`.


* C++, C#, .NET, Node.js are preserved correctly.


* **Similarity and title:**

* If `sentence-transformers` (MiniLM) is installed, semantic similarity is used for projects and titles. If not, it falls back to lexical (word overlap) matching, so code does not break.


* **Fresher handling:**

* If the JD does not ask for a factor (no experience, no certificate) or the candidate has no data for it, that factor is removed and the remaining weights are adjusted again to 100%.


* So freshers are not punished for having no job title or experience.


* If the score comes below 50 but keyword and similarity both have some match, the score is lifted a little towards 50 so a real match is not crushed by empty optional factors.


* **Output:** each factor gives a score and an evidence line (example: "Matched 6 of 8 required keywords. Missing: ..."), so the result can be explained.

## **Date:** 26 Sep 2026

**Subject:** **LLM Score, Final ATS Score and Ranking**

* **LLM score:**

* The Ollama model (`llama3.2` by default) gets the resume JSON and JD JSON and returns `{"score": ..., "reason": ...}`.


* The prompt says to use only the information present in the JSON and not to invent anything.


* The prompt gives the same factor weights as the rule-based part, and does not punish freshers for no experience.


* Temperature is 0 and format is JSON so the output stays consistent.


* Score reading is safe: it handles JSON, code fences, `78/100`, `score: 78`, and rejects values outside 0-100.


* Model name, URL and timeout can be changed by environment variables: `OLLAMA_MODEL`, `OLLAMA_URL`, `OLLAMA_TIMEOUT`.


* **Final score:** `60% rule-based + 40% LLM`. If Ollama is down or gives a bad response, the final score is the rule-based score only, so the pipeline never breaks.


* `compute_final_ats(jd, resume)` returns rule-based score, LLM score, LLM reason, final score and the factor details. Use `use_llm=False` to run rule-based only.


* **Ranking:**

* Candidates with an `ats_score` are sorted high to low.


* Equal scores get the same rank (example 1, 2, 2, 4).


* **Next steps:**

* Test with real resumes and JDs from the DB and check whether the scores look reasonable.


* Store `final_ats_score` in `ats_score` column of the `candidate` table and run ranking.


* Tune weights (`WEIGHTS`, 60/40 blend) after checking results.
